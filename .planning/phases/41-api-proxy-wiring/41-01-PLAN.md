Three fixes:

1. **Add health endpoint rewrite** to `next.config.ts`. Currently only `/api/v1/:path*` is proxied. The `api.health.check()` in api.ts calls `/health` which hits the Next.js server (404), not Express. Add a rewrite:
   ```
   { source: '/health', destination: `${process.env.NEXT_PUBLIC_API_URL}/health` }
   ```
   Also add `/health/live` and `/health/ready` rewrites (backend has these probes from Phase 27).

2. **Fix health check path** in `api.ts`. The health check currently calls `/health` — this is correct with the new rewrite rule. No change needed if rewrite is added. But also add the live/ready variants to the api object for completeness:
   ```ts
   health: {
     check: () => fetch('/health').then(r => r.json()),
     live: () => fetch('/health/live').then(r => r.json()),
     ready: () => fetch('/health/ready').then(r => r.json()),
   }
   ```

3. **Verify `.env.example` alignment**. The frontend `.env.example` already has `NEXT_PUBLIC_API_URL=http://localhost:3000`. The backend `.env.example` should document `ALLOWED_ORIGINS` to include the frontend URL. Check backend `.env.example` — if `ALLOWED_ORIGINS` is not documented with the frontend URL, add a comment noting it should include `http://localhost:3001` for development. Do NOT change backend .env.example if it already covers this.

**What to avoid:** Do NOT add Next.js API route handlers (app/api/) — the rewrite-based proxy is the correct pattern for this architecture. Do NOT change the backend CORS config itself — the proxy means browser requests go to Next.js origin, not Express directly, so CORS is irrelevant for proxied requests.

<task type="auto">
  <name>Task 2: Build verification and auth token flow audit</name>
  <files>frontend/src/lib/hooks.ts, frontend/src/middleware.ts</files>
  <action>
Two verifications:

1. **Run frontend build** to confirm all TypeScript compiles and Next.js config is valid:
   ```bash
   cd frontend && npm run build
   ```
   Fix any errors. The build must succeed — this proves all hooks, types, and config are valid.

2. **Audit auth token forwarding chain** — verify these three links work together:

   **Link 1: Frontend → Token.** `useApiToken()` calls `getToken({ template: 'supabase' })` with fallback to `getToken()`. The `supabase` template produces a JWT with `sub` claim containing the Clerk user ID. The plain `getToken()` produces a standard Clerk session JWT. Both are valid Bearer tokens.

   **Link 2: Proxy → Forwarding.** Next.js `rewrites()` forwards all headers including `Authorization` to the destination. This is default Next.js behavior — no special config needed. Verify this by reading the Next.js docs note: rewrites are server-side proxies that forward the original request headers.

   **Link 3: Backend → Verification.** `auth.js` extracts Bearer token, decodes JWT header, tries Clerk JWKS verification (checks RS256 signature against `CLERK_ISSUER_URL` JWKS endpoint), falls back to Supabase `auth.getUser()`. The Clerk path needs `CLERK_ISSUER_URL` env var on the backend.

   **Potential issue:** If `useApiToken()` gets a Supabase-template JWT from Clerk, the backend's Clerk JWKS verification may fail (different issuer/signing key than standard Clerk JWT), and then Supabase fallback would also fail if the token isn't a real Supabase token. **Fix if needed:** Simplify `useApiToken()` to use plain `getToken()` (standard Clerk JWT) which the backend's Clerk JWKS path will verify correctly. Only change this if analysis confirms the template token won't verify against Clerk JWKS.

   Read `backend-express/middleware/auth.js` fully to understand what claims it checks. If the Clerk JWKS path verifies `iss` against `CLERK_ISSUER_URL`, then the frontend must send a standard Clerk JWT (not a custom-template one) for this path to work.

   **If fix needed:** Change `useApiToken()` to:
   ```ts
   const token = await getToken()
   ```
   Remove the `template: 'supabase'` attempt. The Supabase template was for the iOS app's direct Supabase access — the web frontend goes through Express which has its own Supabase service key.

**What to avoid:** Do NOT modify the backend auth middleware — it's well-tested (Phase 33, 26 auth tests). Only adjust the frontend token acquisition if needed. Do NOT add new dependencies.
