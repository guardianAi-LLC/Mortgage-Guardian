**Established patterns:**
- Backend is a Node 20 Alpine container (`backend-express/Dockerfile`). Railway is the long-running container host; Vercel hosts the same API rewritten via `vercel.json`.
- Env vars flow via Railway dashboard for the deployed backend; `backend-express/.env.example` documents required keys.
- Phase 54 introduced `PLAID_ENCRYPTION_KEY` as a Railway env; same pattern applies.

**Constraining decisions:**
- 55-RESEARCH.md: ClamAV daemon on Railway with `clamscan` npm is the primary path. `Dockerfile` exists, so the Phase 04 stub's "no daemon support" deferral no longer applies.
- 55-CONTEXT.md: sync, sub-second feel on happy path. clamd-over-TCP from same Railway project gives ~50–300ms.
- 55-RESEARCH.md pitfall: ClamAV needs ≥4 GB RAM for signature DB.

**Out of scope (per 55-CONTEXT.md):**
- Application code changes (those land in 55-02 and 55-03).
- Per-tenant scan policy or admin UI.
- Retroactive scanning of existing documents.
</context>

    <option id="railway-only">
      <name>Railway only — ClamAV daemon path</name>
      <pros>Single scan path. Lowest latency (~50–300 ms). $0 marginal cost. Aligns with research recommendation. Vercel becomes preview/edge-routing only, not the upload endpoint.</pros>
      <cons>Vercel functions must NOT serve `/v1/documents/process`. Confirm routing.</cons>

      <cons>Two scan engines to maintain. Cloudmersive adds per-call latency and a third-party data path for sensitive mortgage docs. Higher cost beyond 800 free calls/month. Surface area doubles.</cons>

<task type="auto">
  <name>Task 2: Provision ClamAV Railway service + wire backend env</name>
  <files>backend-express/.env.example, backend-express/RAILWAY-DEPLOYMENT.md</files>
  <action>
1. Via `railway` CLI from `backend-express/`:
   - `railway login` if not already authenticated (auth gate — surface as `checkpoint:human-action` if `railway whoami` fails).
   - Create a new service in the same project, using the official image `clamav/clamav:1.4_base` (the `_base` tag is the one with freshclam-already-run signatures bundled; saves a long first-boot freshclam round-trip).
   - Configure the service:
     - Memory: 4 GB minimum (research-flagged: 2 GB OOMs at startup with current sig DB).
     - Volume mounted at `/var/lib/clamav` so signatures persist across restarts.
     - Expose port 3310 on Railway's private network (NOT public).
     - Env on the clamav service: `CLAMAV_NO_FRESHCLAMD=false`, `CLAMAV_NO_CLAMD=false` (defaults, listed for clarity).
   - On the backend (api) service, add env vars:
     - `CLAMAV_HOST=<clamav-service>.railway.internal` (Railway's internal DNS — value comes from Railway dashboard once the sidecar is up).
     - `CLAMAV_PORT=3310`.
     - `CLAMAV_TIMEOUT_MS=30000`.

2. Update `backend-express/.env.example` with the three new keys + a comment line explaining that `CLAMAV_HOST` is the Railway internal DNS name of the sidecar service in production and `127.0.0.1` (or empty, to disable scanning) for local dev.

3. Update `backend-express/RAILWAY-DEPLOYMENT.md`:
   - Add a "ClamAV sidecar" section under deployment topology.
   - Document the 4 GB RAM requirement, the persistent volume, and the internal-DNS hostname pattern.
   - Note: do NOT expose port 3310 publicly — clamd has no authentication layer.

Do NOT:
- Use the plain `clamav/clamav:1.4` tag without `_base`. That image runs freshclam at first boot and can take 5–10 minutes to be ready, which makes the smoke test in Task 3 flaky.
- Persist the volume on the api service. The volume belongs to the clamav service.
- Set `CLAMAV_HOST` to a public address. Internal DNS only.
  </action>
  <verify>
1. Railway dashboard shows the clamav service `RUNNING`, healthy, with the volume attached.
2. `railway logs --service clamav` shows `clamd started` and a freshclam line like `Database test passed`.
3. `railway variables --service api | grep CLAMAV` returns the three new vars.
4. `cat backend-express/.env.example | grep CLAMAV` shows the three keys documented.
  </verify>
  <done>ClamAV service is running on Railway with 4 GB RAM and a persistent volume. Backend env has the three CLAMAV_* vars. `.env.example` and `RAILWAY-DEPLOYMENT.md` updated.</done>
</task>

<task type="checkpoint:human-verify" gate="blocking">
  <what-built>
- ClamAV daemon running as a Railway sidecar service with persistent signature volume
- Backend env wired with `CLAMAV_HOST` / `CLAMAV_PORT` / `CLAMAV_TIMEOUT_MS`
- Docs updated (`.env.example`, `RAILWAY-DEPLOYMENT.md`)
  </what-built>
  <how-to-verify>
End-to-end reachability and signature freshness — do all three before approving:

1. From the api Railway service shell (`railway shell --service api`), run:
   ```
   nc -zv $CLAMAV_HOST $CLAMAV_PORT
   ```
   Expect `succeeded` / `open`.

2. Send a PING to clamd over TCP from the same shell:
   ```
   (printf 'zPING\0'; sleep 1) | nc $CLAMAV_HOST $CLAMAV_PORT
   ```
   Expect `PONG`.

3. EICAR live-fire test from the same shell:
   ```
   printf 'X5O!P%%@AP[4\\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*' > /tmp/eicar.com
   (printf 'zINSTREAM\0'; \
    printf '\0\0\0\x44'; cat /tmp/eicar.com; \
    printf '\0\0\0\0') | nc $CLAMAV_HOST $CLAMAV_PORT
   ```
   Expect a response containing `Win.Test.EICAR_HDB-1 FOUND` (engine name may vary slightly between sig DB versions).

4. Signature age check (on the clamav service): `railway run --service clamav -- freshclam --version` should report a database date within the last 24 h.
  </how-to-verify>
  <resume-signal>Type "approved" when PING returns PONG and EICAR test reports `FOUND`. If anything fails, describe the failure mode (no response, sig DB stale, OOM) so we can fix in this plan rather than carrying the failure forward.</resume-signal>
