**Prerequisites (must be complete before this plan runs):**
- 55-01-SUMMARY.md: Cloudmersive env vars (`CLOUDMERSIVE_API_KEY`, `CLOUDMERSIVE_BASE_URL`, optional `CLOUDMERSIVE_TIMEOUT_MS`) are wired into config and validated at boot.
- 55-02-SUMMARY.md: `services/malwareScanService.js` exports `scanBuffer(buffer)` and `MalwareScanError`. The service hits the Cloudmersive HTTPS scan endpoint, sets `engine: 'cloudmersive'` on success, and translates HTTP 429 (quota exhausted), 5xx, and network/timeout errors into `MalwareScanError`.

**Established patterns:**
- `validateFileContent(buffer, claimedFileName)` already exists in `fileValidation.js` and runs the magic-byte (`file-type`) check + extension/MIME reconciliation. It's the natural place to fan out into scan + encryption checks.
- Documents route uses Joi at the boundary and returns JSON `{ error: '...' }` on 4xx — keep that shape.
- Error logging uses Winston child loggers; existing scan logs should use `createLogger('upload-security')`.

**Constraining decisions:**
- 55-02 service throws `MalwareScanError` on every infra failure (network, timeout, 5xx, 429 quota). The route MUST translate that into a 502 — never let the upload land in storage when the scan didn't conclusively pass.
- 55-RESEARCH.md pitfall #4: encrypted PDFs can scan as "clean" because the scanner can't decode the content. Short-circuit BEFORE scanning.
- 55-CONTEXT.md scope: no password-prompt UI. Just reject with a clear message.
- Cloudmersive is an HTTPS call from Vercel functions. Expected latency is ~200–800 ms per scan (vs. <50 ms for a local TCP scanner). With the existing magic-byte check + storage write, a 25 MB upload needs to fit under the Vercel function timeout. The default Hobby timeout is 10 s — production should run on Vercel Pro (60 s default, configurable) to keep headroom. Flag this in 55-04's runbook; do not change `vercel.json` here.
- Cloudmersive free tier is 800 scans/month and the paid tier is also capped. When the quota is exhausted the API returns HTTP 429, which 55-02 surfaces as `MalwareScanError`. The route should still 502, but log a distinct `reason: 'scan_quota_exhausted'` tag so oncall can act on it (the 55-04 runbook will document the recovery flow).

**Issues addressed:**
- The Phase 04 stub at `fileValidation.js:255` (`return { scanned: false, reason: '...' }`) is removed in this plan. Search-and-destroy: nothing in the codebase should still reference `scanned: false` as a success state.

**Out of scope:**
- Docs/runbook updates (those are 55-04).
- Retroactive scans (per 55-CONTEXT.md).
- Switching the Vercel plan or editing `vercel.json` (note for 55-04 only).

- Add a try/catch around `scanBuffer` that returns clean on error. That is the exact pitfall #1 from 55-RESEARCH.md — and with Cloudmersive it's especially dangerous because a 429 quota error would silently let unscanned uploads through.
- Move the magic-byte check or the size limit. Those gates are already correct.
- Hard-code the Cloudmersive engine identifier anywhere other than the success return — the engine string lives in the service so 55-02 stays the single source of truth.

<task type="auto">
  <name>Task 2: Wire upload route to fail-closed on scan results</name>
  <files>backend-express/routes/documents.js</files>
  <action>
1. Find the upload handler in `routes/documents.js` (the one calling `validateFileContent`). The path varies slightly across phases — `grep -n "validateFileContent\|scanFileContent" routes/documents.js` to locate.

2. Restructure the handler so the gates run in this order, each gate short-circuiting the response:
   a. Magic-byte validation via `validateFileContent` (already there — keep).
   b. `scanResult = await scanFileContent(buffer, detected.ext)` wrapped in `try/catch`:
      - On `MalwareScanError` (catch block): inspect `err.code` / `err.status` (set by 55-02). If the underlying cause was a 429 quota response, log `error` with `{ userId, reason: 'scan_quota_exhausted', err: err.message }`. Otherwise log `error` with `{ userId, reason: 'scan_unavailable', err: err.message }`. Either way, return `502 { error: 'Upload could not be safety-checked. Please try again.' }`. No file persistence.
      - On returned `{ scanned: false, clean: false, reason: 'encrypted_pdf', message }`: return `400 { error: message }`. No file persistence.
      - On returned `{ scanned: true, clean: false, threats }`: log `warn` with `{ userId, threats, sha256Hash: hash(buffer) }` (NEVER the buffer content), return `400 { error: 'This file appears unsafe and was not accepted.' }`. No file persistence.
      - On returned `{ scanned: true, clean: true }`: proceed to existing storage write path.

3. Use `crypto.createHash('sha256').update(buffer).digest('hex')` for the hash; this is the only thing we keep for telemetry from a caught file. 55-RESEARCH.md open question #4: log hash, not bytes.

Do NOT:
- Persist the file before the scan returns. The whole point of sync scanning is no pre-scan storage window. The current handler may write to MinIO/Supabase early — move that AFTER the clean verdict.
- Leak the threat name or the Cloudmersive engine identifier to the user in the response body. "This file appears unsafe" is the only UX (55-CONTEXT.md). Log details server-side.
- Return 200 with a "scanned: false" body and let the client decide. Hard reject only.
- Retry the scan inline on `MalwareScanError`. Retries belong in the service layer (55-02) or in a future async pipeline — adding them here would blow past Vercel's function timeout on a quota-exhausted day.
  </action>
