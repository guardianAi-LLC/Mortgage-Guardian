**Tech stack available:** Node.js/Express, Supabase PostgreSQL, node:crypto, Joi, Jest. AES-256-GCM + HKDF-SHA256 per-user key derivation already used for documents.

**Established patterns:**
- `documentEncryptionService` — master key from env (`DOCUMENT_ENCRYPTION_KEY`, 64-hex), HKDF info string per user, pack format `iv(12) | authTag(16) | ciphertext(N)` in a single Buffer.
- Env validation via Joi in `utils/envValidator.js`.
- Supabase migrations as numbered SQL files in `backend-express/migrations/`.

**Constraining decisions:**
- Migration must be additive only — do NOT drop or alter the existing `access_token TEXT` column in this plan; backfill happens in 54-04, drop in 54-05.
- Reuse the document encryption pattern verbatim, with a SEPARATE key (`PLAID_ENCRYPTION_KEY`) — Plaid token compromise should not require rotating the document encryption key and vice versa.

**Issues being addressed:** Tokens currently stored as plaintext in `plaid_items.access_token` (the migration file itself flags this: "Should be encrypted in production").
</context>

<task type="auto">
  <name>Task 1: Create plaidTokenEncryptionService with HKDF-derived per-user keys</name>
  <files>backend-express/services/plaidTokenEncryptionService.js, backend-express/utils/envValidator.js</files>
  <action>
Create `backend-express/services/plaidTokenEncryptionService.js` mirroring the structure of `documentEncryptionService.js`:
- Singleton with lazy initialization; master key from `process.env.PLAID_ENCRYPTION_KEY` (64 hex chars → 32 bytes), HKDF-SHA256 to derive per-user 32-byte key with info string `plaid-token:${userId}`.
- `encrypt(userId, plaintextString)` → returns Buffer packed as `iv(12) | authTag(16) | ciphertext(N)`.
- `decrypt(userId, packedBuffer)` → returns plaintext string. Throws on auth tag mismatch.
- Both methods use `aes-256-gcm` via `crypto.createCipheriv` / `crypto.createDecipheriv`.
- Export helper `encryptForStorage(userId, token)` → base64-encoded packed buffer (convenient for storing in TEXT column without binary handling). Also `decryptFromStorage(userId, b64)`.

Then add `PLAID_ENCRYPTION_KEY` to `utils/envValidator.js`:
- Joi pattern: 64 hex chars, required in production, optional in test/dev (mirrors how DOCUMENT_ENCRYPTION_KEY is handled).
- Error messages following existing convention.

Do NOT modify `documentEncryptionService.js` — Plaid uses a separate key on purpose. Do NOT hand-roll any crypto; reuse node:crypto primitives exactly as documentEncryptionService does.
  </action>
  <verify>
1. `node -e "require('./backend-express/services/plaidTokenEncryptionService')"` loads without error when PLAID_ENCRYPTION_KEY is set.
2. Inline round-trip: `const s = require('./backend-express/services/plaidTokenEncryptionService'); const c = s.encryptForStorage('user-1', 'access-sandbox-xxx'); console.log(s.decryptFromStorage('user-1', c) === 'access-sandbox-xxx')` prints `true`.
3. Decrypting with a different userId throws (HKDF info string mismatch yields auth-tag failure).
  </verify>
  <done>Service exists, env validation added, manual round-trip verified, cross-user decrypt fails closed.</done>

  <action>
Create migration `006_plaid_token_encryption.sql`:
- `ALTER TABLE plaid_items ADD COLUMN access_token_encrypted TEXT;` (TEXT holding base64 from encryptForStorage — avoids BYTEA serialization concerns through PostgREST).
- `ALTER TABLE plaid_items ADD COLUMN encryption_version SMALLINT DEFAULT 1 NOT NULL;`
- `ALTER TABLE plaid_items ALTER COLUMN access_token DROP NOT NULL;` so new rows written via 54-02 can leave plaintext NULL.
- Index: `CREATE INDEX idx_plaid_items_encryption_version ON plaid_items(encryption_version);` (used by backfill script in 54-04 to find rows still on plaintext).
- Header comments matching the style of `001_plaid_tables.sql`, including a note that `access_token` column will be dropped in migration 008 (Phase 54-05) after backfill completes.

Do NOT touch `plaid_accounts` or `plaid_transactions` — those don't hold tokens.
