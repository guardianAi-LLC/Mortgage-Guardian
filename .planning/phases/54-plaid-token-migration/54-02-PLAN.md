<objective>
Refactor backend Plaid routes so clients send `item_id` instead of `access_token`. The server resolves the access token from `plaid_items` (decrypted via 54-01) after verifying the authenticated user owns that item.

Purpose: Tokens never travel from client → server again. The access_token is purely a server-side secret.
Output: New `requireItemOwnership` helper, updated routes (`/accounts`, `/transactions`, `/item`, `/item/webhook`, `DELETE /item`), updated Joi schemas, updated route tests.
</objective>

<task type="auto">
  <name>Task 1: Add resolveTokenByItemId with ownership check + Joi schema updates</name>
  <files>backend-express/services/plaidDataService.js, backend-express/schemas/plaid.js</files>
  <action>
1. In `plaidDataService.js`, add `async resolveTokenByItemId(userId, itemId)`:
   - Query `plaid_items` `WHERE item_id = $1 AND user_id = $2` (Supabase `.select('access_token, access_token_encrypted, encryption_version').eq('item_id', itemId).eq('user_id', userId).single()`).
   - If no row: return `{ success: false, code: 'not_found' }`.
   - If row exists: reuse the decrypt-or-fallback logic from `resolveUserAccessToken` (extract a private `_decryptRow(userId, row)` helper to keep both methods DRY).
   - Return `{ success: true, accessToken }`.
   - Log only `itemId` and `userId` — NEVER the resolved token.

2. In `schemas/plaid.js`, for each of `accountsSchema`, `transactionsSchema`, `itemSchema`, `updateWebhookSchema`, `deleteItemSchema`:
   - REMOVE `access_token` field.
   - ADD `item_id: Joi.string().min(1).max(255).required()`.
   - Use `Joi.object({...}).unknown(false)` to actively REJECT requests that still include `access_token`. Joi's default strips unknown keys; switching to `unknown(false)` (or `.strict()`) makes a stale client surface a clear 400 instead of silently failing later.

Do NOT change `exchangeTokenSchema`, `linkTokenSchema`, `sandboxTokenSchema`, or `/webhook` (Plaid → server) — those are unchanged.
  </action>
  <verify>
1. Unit test for `resolveTokenByItemId`: mock Supabase row with encrypted token → returns decrypted; wrong userId → `{ success: false, code: 'not_found' }`.
2. Joi schemas: `accountsSchema.validate({ access_token: 'x' })` errors; `accountsSchema.validate({ item_id: 'abc' })` succeeds.
  </verify>
  <done>Resolver enforces ownership server-side, schemas demand item_id and reject access_token.</done>
</task>

<task type="auto">
  <name>Task 2: Refactor /accounts, /transactions, /item, /item/webhook, DELETE /item to use item_id</name>
  <files>backend-express/routes/plaid.js</files>
  <action>
For each of the five endpoints listed:
1. Replace `const { access_token, ... } = req.body` with `const { item_id, ... } = req.body`.
2. Resolve: `const result = await plaidDataService.resolveTokenByItemId(req.user.id, item_id);`
3. On `!result.success`: return 404 `{ error: 'item_not_found', message: 'No Plaid item found for the current user with that item_id' }`. This same response covers "item doesn't exist" AND "item belongs to a different user" — no leakage of existence.
4. Pass `result.accessToken` to the downstream `plaidService.*` call (signatures unchanged).
5. NEVER log the access token. Logs should reference `item_id` and `req.user.id` only.

Also update JSDoc blocks above each endpoint to reflect the new request-body contract.

Do NOT touch `/link_token`, `/exchange_token`, `/items` (GET), `/webhook` (Plaid callback), `/sandbox_public_token`, `/test`.
  </action>
  <verify>
1. `curl -X POST /v1/plaid/accounts -H 'Authorization: Bearer <jwt>' -d '{"item_id":"<owned-item>"}'` returns 200 with accounts.
2. Same call with `{"access_token": "xxx"}` and no item_id returns 400 (Joi rejects unknown key + missing required).
3. Same call with another user's item_id returns 404 with `item_not_found`.
  </verify>
  <done>All five endpoints require item_id, enforce ownership, return 404 for non-owned items, never accept access_token from the body.</done>
